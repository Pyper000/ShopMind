# ShopMind 下一步（2026-10-18）

## 当前模型选择

原 Ecommerce Agent 已有一套检索增强链路：SearchAgent 调用商品检索工具；`CatalogSearchUseCase` 按 embedding 向量召回，Qdrant 返回候选，再用可选 reranker 精排；服务异常时退化为中文关键词 2-gram。MainAgent 负责理解与调度，TradeAgent 负责订单操作，不是推荐排序器。

个性化偏好也有基础：`PreferenceSelector` 可用 embedding 按当前 query 选择相关的正向偏好，用户明确的 dislike 始终保留。不过向量相关偏好选择默认关闭；这不是双塔模型，也没有用用户点击、加购、购买行为训练 user/item 表征。

当前 Vercel 展示版是另一条精简链路：规则先按价格、配送、排除项过滤模拟目录，再由 LLM 选商品；没有接入 Ecommerce Agent 的 Qdrant、embedding、reranker 或双塔。两套实现不能在介绍里混称为同一个已上线能力。

**优先级判断：现在不做双塔。** 双塔适合在大量商品和持续交互数据下做大规模候选召回，至少需要曝光、点击、收藏/加购、购买等带时间与用户上下文的行为数据，以及负样本、冷启动和离线评测。当前只有模拟目录和少量人工场景，训练出的排序既无法可信验证，也不能代表真实个性化。

当前最小可验证方案：LLM 从对话中抽取场景与用户明确表达的偏好；业务规则执行已有/缺少/暂缓、预算和配送硬约束；目录按场景/品类/属性召回；基于明示偏好和商品属性做可解释排序。积累真实交互后，再评估 embedding 召回和 rerank；只有行为量足够且离线指标证明有增益时，才评估双塔。

## 当前链路分层

- **交互层**：前端对话、清单逐项按钮、预算和优先级选择；用户确认后发送结构化 `checklist`，不再只发送一段自然语言。
- **理解层**：首轮 LLM 负责识别生活任务、关键条件、具体清单和需要追问的问题。
- **状态层**：保存本轮任务状态：`tasks`、`must_buy`、`optional`、`reusable`、`not_buy`、`unknowns`、预算和偏好。
- **规则层**：代码执行确定性约束，包括库存、配送地、预算上限、已有/暂缓排除、可购买品类召回和方案金额计算。规则层不负责“理解语气”，也不替模型编理由。
- **候选层**：从规则过滤后的目录按待购槽位和同义词缩小候选范围；当前是低成本关键词召回，不是双塔或向量检索。
- **解释层**：第二次 LLM 只在候选范围内生成商品卡片的选择理由、取舍、不足和下一步问题；它不能改变价格、库存或预算结果。
- **测评层**：前端记录轮次、延迟、清单状态、候选覆盖、比较行为和主观评分；CSV 是本地导出，不依赖后端汇总。

确认清单后的请求现在跳过重复的“需求解析调用”，但保留商品解释调用：首轮是“理解和列清单”，确认后是“基于结构化状态筛选和解释商品”。这是减少重复工作，不是取消个性化上下文。

## 产品优先级

### P0：先跑通可验证的最小闭环

- **对话与清单**：场景条件不足时先问会改变清单的问题；边界够了再列清单。清单行是可核对的具体物品，不再用“电子设备、衣物鞋履、日常用品”代替。证件、车票和 App 等不可购买事项单列为“出发前提醒”，不进入商品搜索。
- **状态与推进**：状态文案采用“已有 / 需要购买 / 还没确认”；可选项用“已有 / 想购买 / 先不买 / 还没确认”。未标记项目也必须按“还没确认”传给模型。保留用户看到的真实追问文本，确认清单后明确进入候选匹配。
- **个性化**：只使用当前对话明确给出的场景、预算、风格、尺码/舒适度偏好与长期偏好；缺关键选品信息时追问一个具体问题。没有浏览历史或画像数据时，不声称“像淘宝一样懂用户”。
- **目录与缺位兜底**：首批固定验证城市/短途旅行、海边出行、第一次租房、实用送礼。每个重点可购买槽位优先提供两件可比较候选；只有一件时说明目录不足；没有时说明缺位并给出可选下一步，禁止拿不相关商品凑数。
- **卡片与比较**：用两列紧凑、近方形卡片对照同一任务的替代商品。保留商品名、模拟价格、匹配原因、取舍/未知项；替代品不得重复计入总价。窄屏改为单列。
- **预算**：购物方案商品价由代码确定性求和；预算上限按最低候选方案核验。标明模拟价、不含运费、不是真实比价。价格或属性缺失要显示未知，不让模型编造。

本地商品目录从 111 件增加到 128 件，新增旅行/海边的步行鞋、速干衣、防晒外搭、手机防水袋/泳衣，以及租房床品、清洁、照明、收纳和茶叶替代款。数据仍是虚拟样例；这只能提高 Demo 的场景覆盖，不代表市场价格、库存或真实推荐效果。商品阶段现在先用槽位关键词及有限同义词从规则过滤后的目录召回候选，再让 LLM 选型，避免把整本目录都塞进模型；没有候选时不拿无关商品补位。用户明确确认清单后，服务端强制推进商品匹配，避免模型重复返回清单阶段。

此规则召回是低成本的 MVP 基线，不是语义检索或个性化模型。它可能漏掉没有词面重合的相关商品，后续应以候选覆盖率评估是否需要接入 Ecommerce Agent 里的 embedding/Qdrant，而不是直接跳到双塔。

### P1：等 P0 测试有结果再决定

- 给明确偏好建立可撤回的轻量档案，增加“本次使用了哪些偏好”的解释与编辑入口。
- 先用固定的场景/属性规则或现有 embedding 召回 + rerank 做候选排序对照，不训练双塔。    图片、加更多场景；不要为了“全品类覆盖”继续无差别堆商品。

## 测评口径

`scenario_metrics` 与 `scenario_transcripts` 用 `scenario_id` 关联。文本逐字记录是判断模型是否理解、有没有跳步或虚构的主证据；截图只补充界面状态与卡片布局，尤其清单勾选、确认推进、同槽位商品对比这三处。每个场景建议截 2 张：清单核对态、商品比较态。CSV 保存截图相对路径。

场景回归指标：

- 追问是否可见且必要；轮次是否足以把模糊目标推进到方案。
- 清单具体度、购买项/非购买提醒分离、重复项率。
- 购买槽位商品覆盖率 = 至少返回 1 个相关候选的已确认购买槽位 / 已确认购买槽位。
- 可比较率 = 至少有 2 个相关候选的购买槽位 / 有候选的购买槽位。
- 错误推荐率 = 已有、暂缓、未确认物品仍被推荐的数量 / 所有推荐项。
- 预算求和正确率、候选理由/取舍/未知信息完整率、调用成功率与响应耗时。
- 真实用户测试另记任务完成率、轮次/耗时、满意度、决策信心；场景脚本回归不能冒充真实用户指标。
