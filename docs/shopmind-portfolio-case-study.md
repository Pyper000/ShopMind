# ShopMind｜AI 产品经理项目案例

个人AI产品项目 · 2026-10-25 · [完整作品集](portfolio/README.md) · [PRD](shopmind-task-to-plan-prd.md) · [交互原型](portfolio/02_需求与原型/prototype.html)

## 30秒介绍

我从第一次欧洲旅行的准备经历出发，发现自己要在经验内容、备忘录和电商之间反复整理、核对与比较。我把这个问题拆成“准备什么、已有是否可用、什么才需要购买”，设计了ShopMind的模块清单和显式状态流程，再让Agent只处理确认缺口。

目前本地MVP具备模板/开放场景、缺口检索、反馈、可选账号和授权记忆、人工模板发布回退。最新全量395个测试通过、前端构建通过；真实用户效果尚未证明，旅行家庭多轮与一个高UV错误仍需完善。

## 背景：证据如何影响定位

定性：创始人经历、n=5群友摘要、A–D、CAT-01与TRIP-02提供不同准备策略；有人靠记忆和当地补购，有人先基础后升级，且样本可能重叠。

定量：没有去重后的任务规模、漏项率或耗时基线；工程测试与14Query检索探索集只能证明工程问题，不能代替需求验证。

产品判断：优先陌生、多品类、高准备成本任务；不把所有旅行用户设成目标，不把更多购买作为成功。详见[研究判断](portfolio/01_调研分析/研究与机会判断.md)。

## 目标：业务与模型分开

业务目标是假设性地降低真实任务的整理、核对与补救成本，以有效完成、时间、关键遗漏、冗余和决策信心验证。

模型目标是正确理解对象/约束、形成具体模块、保留多轮事实、遵守目录与用户状态。模板快路不必调用模型；无供给、信息缺失与用户不买都可以是正确结果。

## 行动：做了哪些产品决策

1. 把建议属性（必备/按需）和用户状态（已有/准备/未知/不需要）分开；证件等非商品只携带/办理。
2. 模板与新场景共用ShoppingPlan；对象冲突先阻断，再考虑语义路由，避免“健康成年狗”命中猫。
3. MainAgent/Orchestrator统一维护方案，SearchAgent只检索确认缺项；价格/预算/品类硬约束由代码处理。
4. 一键清单反馈和购买自报建立观测入口；游客保存与授权长期记忆分开，支持撤回/清除。
5. 新场景只进入去标识化候选，结构评测后人工发布版本，可回退；不自动训练或发布。
6. 从人工反馈增加天气、数量和同行儿童的旅行要求；以失败样例更新验收，不只追加功能描述。

技术选择：React/TypeScript/Vite负责状态界面；FastAPI/SSE传递计划与候选；AgentScope2.x组织Agent/工具；DeepSeek-V3.2是当前配置模型，尚无正式多模型胜出数据。JSON/SQLite服务本地MVP，Redis/Qdrant等按配置可选。详见[架构选型](portfolio/03_架构与实现/架构与选型.md)。

## 结果：跑通范围与局限

| 结果层 | 证据 | 可以说 / 尚不能说 |
| --- | --- | --- |
| 工程实现 | 本轮395 passed，1 warning；前端build通过 | 可说已有断言通过；未覆盖分支仍有高UV错误 |
| 本地闭环 | 历史SSE/API/实际渲染截图，阶段1–5验收报告 | 可说特定版本本地跑通；不能代表公网同步或真实交易 |
| 检索质量 | 14Query临时参考集、已知槽位过滤探索值 | 可说发现语义召回弱点；不能写正式准确率 |
| 用户价值 | 现有个案、尚无主持式效果对照 | 只能提出机会假设；不能写减少耗时/转化提升 |
| 最新旅行 | 天气基础验收、多轮细分需求与部分实现 | 成人/儿童、天数、活动组合仍待专项验收 |

本轮复现高UV错误，说明“测试通过”必须连同覆盖范围报告。[评测证据](portfolio/04_评测与数据/评测与证据.md)提供原始文件和未执行的A/B方案。

## 复盘与下一步

先修高UV和复杂旅行多轮，再补清单专业审查、相关性金标及同任务可用性对照；真实SKU、正式线上实验与成交归因在供给和身份体系就绪后推进。

核心学习：Agent能返回答案只完成了链路的一部分。要成为可用产品，还要定义状态、边界、失败处理和验证分母，允许结果是“复用已有，不购买”。[阶段复盘](portfolio/05_迭代与复盘/阶段复盘.md)保留每一步判断依据。
