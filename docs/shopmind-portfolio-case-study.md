# ShopMind AI｜生活任务采购决策助手

> 独立 AI 产品作品集案例。网址：xx。商品、价格和账户均为模拟数据，不接真实库存、交易或订单。以下区分已验证事实与待验证假设。

## 30 秒看懂

第一次租房、出行、或第一次当娃/宠爸妈时，用户往往知道大概“要完成什么”，却不确定要核对哪些物品、家里已有多少、哪些真的需要买。通用购物搜索通常从关键词或商品开始；ShopMind 的产品假设是先把生活任务拆成可核对的具体清单，再由用户确认缺口，只为明确待购项找同品类商品。

核心流程：

```text
生活目标 → 场景理解/模板 → 分组的具体清单 → 逐项确认状态
         → 只检索明确待购项 → 解释候选、目录缺口与取舍
```

项目目前证明了本地模板、清单状态和检索链路可运行；尚未证明目标用户确有足够强的需求、清单内容专业正确、推荐有用或产品能提升转化。

## 项目概况

| 项目 | 当前定义 |
| --- | --- |
| 目标用户假设 | 第一次面对一类生活任务、采购经验有限，担心遗漏、重复购买或过度准备的人；未经访谈验证 |
| 核心任务 | 从生活目标形成可核对清单，确认已有与缺口，再为明确待购项检索候选 |
| 当前场景 | 出行、开学、租房、待产住院准备、第一次养猫 |
| 项目角色 | 个人 AI 产品项目：负责产品定义、流程与状态规则、评测口径及本地验收；不代表正式商业团队或线上业务 |
| 当前阶段 | 固定模板与核心交互可在本地演示；内容质量、商品相关性和用户价值待验证 |

## 1. 问题判断：从“找商品”前移到“先判断缺什么”

**待验证的问题假设：**经验不足的用户容易从别人的清单、搜索结果或零散建议开始，再自行检查已有物品、遗漏项、数量、预算和适用条件。这会增加决策负担，也可能导致漏买、重复买或为了不确定的小概率需求过度准备。

**产品机会假设：**如果先让用户看见任务所需的具体项目，并明确区分“物品类型”和“我的购买状态”，用户能更容易确认缺口，也更容易选择暂不购买。

这两点是产品假设，不是已完成用户研究后的结论。目前没有可引用的用户访谈、问卷、任务观察或样本统计。作品集不将个人经验或公开清单观察包装成用户调研结果。

## 2. 产品方案与关键规则

### 从任务到采购决策

1. 用户以生活目标开始，而不必先知道商品关键词。
2. 命中固定场景时，优先返回结构化模板；模板未覆盖的开放需求由 MainAgent 理解，必要时追问。
3. 清单按对象或任务模块展示具体物品、数量/条件，以及“必备 / 按需”分类。
4. 用户逐项标记“已有 / 需要购买 / 不需要 / 还不确定”；未提及不等于已有。
5. 仅对明确待购项调用 SearchAgent，返回同品类候选；模拟目录没有匹配时展示缺口，不拿邻近品类凑数。
6. 用户修改状态、预算或偏好时，只更新受影响的槽位和候选。

### 两组概念分开

| 维度 | 取值示例 | 用途 |
| --- | --- | --- |
| 物品类型 | 必备 / 按需 | 表达清单建议的必要性或触发条件 |
| 用户状态 | 已有 / 需要购买 / 不需要 / 还不确定 | 表达用户对单项的明确判断 |

按需项的“不需要”和“还不确定”不混为一谈；前者是用户作出的决定，后者保留未知状态，两者都不触发搜索。必备/按需使用黄色/绿色视觉分组，桌面、平板、手机分别采用三栏、两栏和单栏布局。

### AI 与确定性逻辑边界

| 组件 | 责任 | 边界 |
| --- | --- | --- |
| 场景模板 | 已知场景下快速提供分组清单 | 模板命中可能不调用模型，不能当成 LLM 质量证据 |
| MainAgent | 理解开放表达、维护方案状态、处理必要追问并组织回复 | 不推断用户没有表达的物品所有权或购买意愿 |
| SearchAgent | 对明确待购槽位召回、过滤和排序候选 | 不改写清单事实，不得跨品类凑数 |
| 规则与商品目录 | 校验品类、价格等可验证约束 | 当前目录与价格为模拟数据，不代表真实可售供给 |
| TradeAgent | 未来交易扩展边界 | 当前关闭；MVP 不创建真实订单 |

场景演示使用实际 LiveChat/API 对话，但模板首轮优先走确定性路径，开放表达或后续问题才可能调用大模型。是否发生模型调用须以事件记录判断。

## 3. 本地验证：跑通不等于有效

| 证据 | 当前结果 | 能说明什么 / 不能说明什么 |
| --- | --- | --- |
| 浏览器清单验收 | 全新 session 实测待产、租房、第一次养猫；待产孕妇/宝宝/陪护人 17/8/5 项，租房 3 模块，养猫 5 模块；桌面/平板/手机为 3/2/1 栏 | 页面收到并展示了模板分组；不证明每条建议、数量或专业内容正确 |
| API 核心链路 | 出行、开学、租房“清单—确认—补充”9/9 阶段通过；这轮 `model.call=0` | 固定模板和目录交互可运行；不代表模型理解质量 |
| 检索探索集 | 14 条 Query、7 个槽位、K=8；已知槽位过滤时临时 Recall@8 为 0.743、Precision@8 为 0.809、MRR 为 0.857 | 只提供问题定位信号；170 个候选的人工标签仍未完成、14 条 Query 均待复核，不是正式 Gold 指标或“推荐准确率” |
| 模型调用 | 一次租房开放式追问观察到 DeepSeek-V3.2 调用，模型事件耗时 11.062 秒，无质量评分 | 只能证明该次请求调用了模型；不足以估计时延分布或回答质量 |

当前最重要的限制不是再加 UI，而是证据基础不足：缺少人工复核的清单参考答案、完成标注的商品相关性 Gold、获准使用的真实 SKU，以及真人完成任务的观察。

## 4. AIPM 视角：证据缺口与改进优先级

| 优先级 | 缺口 | 下一步产物与验收方式 | 为什么先做 |
| --- | --- | --- | --- |
| P0 | 商品相关性没有正式金标 | 双人标注现有 170 条候选；对“相关/不相关/待确认”记录属性证据与理由，裁决分歧；补充未参与调规则的 holdout Query。报告 Precision@3/8、Recall@3/8、MRR 及按字面/语义表达的分层结果 | 现有指标高度依赖临时参考集合，无法判断排序/召回是否真的有用 |
| P0 | 清单本身未经独立正确性审查 | 每个重点场景建立有来源的参考清单；两位评审核对必备/按需、数量、条件、遗漏与重复。待产内容另请熟悉当地医院要求的评审复核 | 检索再准也可能把不完整或不适用的任务清单做得更快 |
| P0 | 模拟目录无法证明商品可买、属性真实 | 先确定合法、可持续的数据来源，再建立带价格时间戳、规格、地区配送和下架状态的真实 SKU 小样本；若暂不可接入，继续明确限制，不把模拟数据写成线上能力 | 真实商品事实是商品决策产品的核心数据依赖 |
| P1 | LLM 的增量价值缺少同题对照 | 建 50 条覆盖模糊表达、否定/纠正、多意图、条件补充和超范围的对话集；同题对照模板/规则与 LLM，双人评分槽位解析、追问必要性、状态更新和严重错误 | 需回答“为什么要用模型”，而不是只证明架构里接了模型 |
| P1 | 时延与模型成本样本不足 | 每个场景重复至少 30 次，分开记首条反馈、首份清单、首个商品、整轮结束、模型事件耗时、错误/断联、Token 与账单成本；报告 P50/P95 | 为体验目标与模型成本做可比较的产品决策；不得用一次请求当稳定指标 |
| P2 | 没有真人任务体验或行为结果 | 先做 10–15 位目标用户的主持式试用，每人完成两个任务；记录独立完成、时间、清单增删、重复购买担忧、商品有用性和放弃原因 | 验证“清单是否减轻负担”后再考虑转化实验；小样本不用于宣称 ROI |

以上样本量是首轮研究计划，不是统计显著性承诺。短期建议顺序是：先完成金标与清单审查，再验证模型增量和可靠性，最后进入真人可用性研究；真实业务指标应在接入真实目录/交易并有合适对照后定义。
