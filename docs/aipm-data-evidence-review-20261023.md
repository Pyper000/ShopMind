# ShopMind 数据证据评测（本地，2026-10-23）

## 结论

目前证据支持“固定模板场景下，ShopMind 的本地清单与检索流程可运行”，不支持“AI 已能稳定理解开放需求、推荐准确、用户愿意持续使用或能提升转化”。这轮最大的阻塞不是 UI，而是商品相关性金标尚未完成、清单内容没有独立质量审查、真实用户与真实商品数据均缺失。

本轮只评测本地工作区和隔离服务，未推送或部署。

## 本轮复评

### 商品检索

用当前检索代码重跑了 14 条 ShopMind 核心 Query，覆盖周末海边与首次租房 2 个场景、7 个槽位；7 条字面表达、7 条语义表达，参考集合含 46 个相关 SKU。运行使用本地 `keyword_2gram`，K=8。

| 配置 | 临时参考集 Recall@8 | Precision@8 | MRR | 脚本门禁 |
|---|---:|---:|---:|---|
| 不传购物槽位过滤 | 0.629 | 0.339 | 0.643 | BLOCK |
| 传入已知购物槽位过滤 | 0.743 | 0.809 | 0.857 | BLOCK |

按已知槽位过滤后，字面 Query Recall@8 为 0.971；语义 Query 只有 0.514，且 7 条中有 2 条完全没有召回，床品语义 Query 仅 0.20。当前最明确的技术信号是：槽位过滤在这组样本上减少了跨品类候选，但“用日常表达找到对的商品”仍未被证明。

这些是**临时参考集指标，不是正式 Gold Recall**。标注说明明确候选池不是全量目录；评测使用的 `shopping_task` 是已知槽位，未测用户表达能否先被正确解析成槽位。报告中的 NDCG 不用于结论，因为现有相关性标签没有等级排序。Recall 0.75 是脚本门槛，不是经业务验证的产品验收线。

### 端到端流程与时延

在当前隔离 API `8013` 上，用全新 session 对出行、开学、租房跑了“初始清单—确认单项—补充单项”三阶段，9 个阶段全部通过。初始清单首个计划 SSE 事件为 0.995–1.112 秒，整轮为 1.506–1.553 秒；确认后首个商品候选事件为 0.038–0.055 秒，确认轮整轮为 0.551–0.554 秒；补充轮整轮为 0.542–0.569 秒。六次商品返回的标题/亮点字符串槽位匹配代理值均为 1.00。

这仍是每场景一次的脚本 API 回归，不是浏览器绘制时延、人工相关性 Precision 或用户任务完成率；上述 9 个阶段的 `model.call` 都为 0。租房解释问题只有 1 次真实 DeepSeek V3.2 调用，记录耗时 11.062 秒，没有质量评分，也不足以估计模型时延分布。

浏览器验收已实际渲染待产、租房、首次养猫清单，可证明页面拿到了分组数据；它不验证每个物品是否该列为必备、数量是否准确或商品是否有用。

### 金标与商品数据状态

14 条核心 Query 对应的标注工作簿有 170 行候选，但“人工相关性”“关键属性证据”“标注理由”三列 170 行均为空；复算页 14 条 Query 全部显示“待标注”。因此当前 Recall/Precision 对标注集合高度敏感，不能对外宣称推荐准确率。

另有 67 条通用商品检索 Query 和 22 条品类知识 Query，但它们没有 ShopMind 的场景/购物槽位结构，不能替代清单—商品的端到端金标。现有本地商品目录说明标注使用模拟价格与属性；因此当前结果也不代表真实 SKU、库存、配送区域或售后适配。

### 评测脚本同步问题

现有三场景脚本把租房锚点硬编码为“床品套件”，而当前模板项已细化为“床品套件（床单/被套/枕套）”，第一次复跑在检索前因字符串不相等而中止。之后仅在内存中把该测试锚点替换成当前模板确有且可检索的“台灯”，没有改脚本文件，复跑为 3/3。此处不是服务故障，但说明验收用例与模板更新尚未形成自动同步机制；而精确字符串匹配也会把真实的同义/细化槽位误判为失败。

## 尚缺的数据证据，按优先级

| 优先级 | 缺口 | 下一步证据 | 需要回答的问题 |
|---|---|---|---|
| P0 | 商品相关性金标未完成 | 先双人独立标完现有 170 条候选，允许“相关/不相关/待确认”，记录属性证据和理由；复核候选池外可能的正例并裁决分歧。再新增至少 60 条未用于调规则的 Query，覆盖 5 个目标场景及字面、语义、模糊表达，按槽位分组隔离 holdout。 | Top-3/Top-8 真正有用吗？漏掉了哪些可买商品？错误候选来自检索、槽位解析还是目录缺货？ |
| P0 | 清单内容没有独立正确性评审 | 为每个场景建立有来源的参考清单；两位评审逐项判断必备/按需/不需要/不确定、数量与条件、缺项/重复项。待产清单另请熟悉当地医院要求的专业评审，保留 NHS 英国参考与本地差异说明。 | 清单是否完整、不过度采购，哪些项目因地区/人群/条件而变化？ |
| P0 | 商品目录是模拟数据 | 接入一份获准使用的真实 SKU 快照，至少含价格时间戳、库存、地区配送、规格/属性和下架状态；让标注者按真实属性评商品。 | 推荐能否买到，规格是否满足约束，价格/库存多久过期？ |
| P1 | LLM 开放对话质量样本太少 | 准备 50 条新对话用例，覆盖模糊需求、多意图、否定/纠正、条件补充、超范围与安全敏感表达；为预期槽位、追问点和不应回答内容建立双人评分。对照模板/规则基线，记录解析准确、追问必要性、用户修订和错误严重度。 | 模型相对规则/模板真正增加了什么价值，在哪些话术上会错？ |
| P1 | 时延与成本只有小样本点测 | 按场景重复至少 30 次并做轻量并发；分开统计首条反馈、首份可见清单、首个商品、整轮结束、模型耗时、错误率、token/成本，报告 P50/P95。 | 用户实际等多久，慢请求集中在哪条链路，质量改善的代价是什么？ |
| P2 | 没有真实用户行为与业务结果 | 先做 10–15 位目标用户的主持式可用性试用、每人 2 个任务；记录独立完成率、完成时间、增删改清单比例、状态确认率、商品有用性评分和放弃原因。接入真实购物车/订单后再定义曝光到加购、下单转化的分母和对照组。 | 清单是否减轻准备负担？商品是否被采纳？之后再判断是否影响转化或复购。 |

以上样本量是建议的首轮评测计划，不代表统计显著性承诺。尤其不能把 10–15 人的可用性试用当成转化验证；线上转化样本量应基于届时的基线转化率和可检测差异单独计算。

## 建议的产品决策

下一步先暂停增加 UI 细节，优先补齐 P0：完成商品候选双人标注、冻结一份未参与调规则的 holdout、校验各场景清单内容，并明确真实目录数据来源。之后再做 10–15 人的主持式试用。

在这些证据补齐前，可以把产品描述为“本地可运行、模板场景流程已验证的 ShopMind 原型”；暂不把它描述为“AI 推荐准确”或“已验证能提升转化”。下一次评审建议同时看槽位解析、清单内容、真实 SKU 命中和用户修订，而不是只看一次跑通或字符串匹配率。
