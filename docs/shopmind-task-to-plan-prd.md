# ShopMind 生活任务采购决策 PRD

- 版本：0.3
- 状态：MVP 产品与本地实现基线（2026-10-23；不代表公网部署状态）
- 覆盖场景：出行、开学、租房、待产住院准备、第一次养猫；商品与价格仍为模拟数据

配套作品集总览见 [ShopMind 产品案例](shopmind-portfolio-case-study.md)；本文定义需求、边界与验收口径，不替代数据质量或用户效果证据。

## 1. 产品定义

ShopMind 面向缺乏某类生活任务经验、又不想漏项、重复购买或买错的用户。它从生活目标出发，生成可核对的具体物品清单，让用户逐项确认，再只为明确待购的项目检索商品；对适用条件、数量、取舍和信息缺口作解释。

差异点不是场景推荐、商品组合或下单本身；而是让用户更有把握地完成任务，尤其能看见“可以不买什么”和“选择意味着放弃什么”。用户没有说过的已有物品不能被假定。演示案例里的回答可以是预设的，但必须明确标成案例输入，而非系统默认状态或模型推断事实。

## 2. 相对通用购物助手的边界

| 通用购物助手常见输出 | ShopMind 要交付的决策结果 |
| --- | --- |
| 按场景推荐一组商品 | 先列可核对的具体任务项，再由用户确认缺口 |
| 展示商品与卖点 | 分开表达物品类型（必备/按需）和用户状态（已有/要买/不需要/未确认） |
| 鼓励继续浏览或加购 | 只检索明确待购项；允许结果为“不需要购买”或“当前目录无匹配” |
| 给单品理由 | 说明为什么选、放弃什么、不适合谁、哪些信息未知 |
| 对话后重新推荐 | 把用户补充当作状态变化，更新清单、预算和理由 |

以上竞争对比以用户提供的千问购物助手观察为输入：场景化推荐、组合、追问、比价和下单已不是独占能力。这不是独立竞品实测，不据此断言千问的具体流程或细节。不要把“会追问、会组套、会下单”单独作为差异化证据。

### 与千问购物助手的竞争判断

截至 2026-10-15，阿里巴巴 2026-05-11 的公开介绍称，千问/淘宝购物助手支持开放式需求追问、商品选项和组合推荐、并排比较、下单与订单/物流管理，并可使用淘宝/天猫商品目录、历史订单和评论等生态信息。[阿里巴巴公开介绍](https://www.alibabacloud.com/blog/603104)

| 维度 | 千问/淘宝公开能力描述 | ShopMind 当前 Demo 的位置 |
| --- | --- | --- |
| 场景理解、追问、组套 | 已公开覆盖 | 必须做到基本可用，但不作为独占差异 |
| 目录、评论、历史与交易闭环 | 依托淘宝/天猫生态；商品和交易基础设施明显更强 | 只有模拟目录与静态案例，不应声称更全、更便宜或更能成交 |
| 最小够用与不买建议 | 上述公开介绍不足以判定千问是否具备/不具备该能力 | ShopMind 的产品假设：让“复用已有、暂不购买、为什么不买”成为主结果 |
| 解释取舍和未知 | 需实际体验具体版本后再比较 | Demo 应在结果中展示选/弃理由与未知信息，但静态文案尚非能力证明 |

因此不能把“千问不会告诉用户不买”当作既定事实。ShopMind 的竞争主张应表述为：**我们专门把最小购买集合和可不买路径作为决策目标，并用显式状态与规则约束方案**；是否能比通用助手做得更好，需要同任务实测。

ShopMind 的可主张差异是**采购决策纪律**：以任务完成为目标，以明确的用户陈述为状态依据，以业务约束校验预算和品类，以“可不买”及双向取舍帮助用户做决定。它目前是要在 Demo 中被证明的产品假设，不是已经建立的技术壁垒；长期优势仍需通过可信目录数据、状态更新质量和评测结果积累。

## 3. 用户与成功任务

目标用户：第一次面对一种生活任务、缺乏经验，同时不希望漏项、重复购买或为低概率需求过度准备的人。

当前模板场景：周末海边出行、一般出行、开学准备、首次租房、待产住院准备、第一次养猫。场景模板按模块列出具体物品、数量或触发条件；模板是核对起点，不是对用户实际拥有状态的推断。待产内容以 NHS 英国资料作参考并明确提示以当地生产医院要求为准；涉及宠物健康时提示咨询兽医，不输出医疗建议。

开放场景在模板未命中时由 MainAgent 理解并在必要时追问；模板命中时优先用结构化模板快速呈现清单。用户给出已有物品、明确要买或不需要后，系统只更新对应状态并检索明确待购项。

## 4. 核心 SOP 与交互规则

1. **承接任务**：复述生活目标和已知条件，不先推商品。
2. **收敛边界**：最多问 2 个问题，只问会改变品类、数量或优先级的条件。输入已包含答案时跳过，不重复问。用户只给场景时，不要求其先描述采购品类或担忧；先收敛场景边界，再给清单框架。若无硬预算，不为填槽而追问；可在匹配具体商品前补问。
3. **先给具体清单**：场景命中模板时，展示模板中的具体物品和模块，不以“待产包、婴儿用品、清洁用品”等大类替代实际核对项。每项展示数量、条件或说明（有数据时）；物品类型标为必备或按需，不能把物品类型当作用户购买状态。
4. **接收用户判断**：每项由用户标记状态。必备项可标记“已有 / 需要购买 / 还没确认”；按需项可标记“已有 / 这次要买 / 不需要 / 还不确定”。未知与明确不需要必须分开保存；未提及的项目不能推断为已有。
5. **匹配与比较**：只为用户确认的缺口找商品。模型根据目标、偏好及目录商品事实比较同一任务槽位的候选，说明为什么选、放弃什么、不适合谁和未知信息。备选商品是互斥选项，不相加计入方案总价。
6. **方案级预算校验与调整**：模型负责预算内的选择策略、排序和解释；业务代码依据目录价格计算每个任务槽位的选项、必需小计、可选小计和方案总价，并校验不超过上限。不得让模型凭语言生成或心算价格。用户增加已有物品、删除品类、改变活动/偏好后，重算方案和理由。预算不足时给可完成的最小子集并明确未覆盖目标，不能声称“完整方案”。
7. **简洁展示状态变化**：不重复铺陈整份“变化前/变化后”清单。直接展示更新后的最终方案；仅在相关时用一句“已按你补充的双肩包移除背包采购”等摘要交代变化。

简单单品任务可缩短流程；复杂任务可多一轮确认。每轮只推进一级认知，不机械凑满轮数。

## 5. 主案例验收脚本

以下是**预设案例输入**，不是 ShopMind 对任意用户的默认设定。清单模板及条件以当前 `scene_templates.json` 为准；本表是产品验收用例，不是完整金标：

| 阶段 | 案例内容 | 验收点 |
| --- | --- | --- |
| 用户输入 | “周末去海边两天，帮我准备购物清单” | 用户只给场景也能开始；不要求用户先诊断缺项 |
| 边界追问 | “几个人同行？行李有数量或体积限制吗？” | 最多 2 个会改变清单的问题 |
| 案例回答 | “一个人，我想只带个随身包，家里有个双肩包。” | 只把双肩包记为已有；携带约束明确 |
| 清单框架 | 必备：防晒、换洗、洗漱；已有：双肩包；可选：收纳袋；下水用品为条件项 | 先展示任务槽位；不是所有槽位都默认需要新买 |
| 用户判断 | “轻量少占空间，换洗和洗漱用品家里都有，防晒还没准备。” | 复用已明确物品、确认防晒缺口；不展示冗长双份清单 |
| 最终方案 | 目录内防晒候选与可选收纳方案；同类备选可比较，汇总必需总价并分开可选金额 | 目录外品类不编造商品；无数据的属性明确标未知 |
| 方案总结 | 必买件数、必需总价、可选金额、预算余量和条件待确认项 | 让用户清楚“买几件、多少钱、解决什么、还能不买什么” |

当前虚拟目录可用于演示示例商品与价格；目录没有的防晒效果、容量、耐用性等属性仍需标未知。若用户确认家里有可替代袋子，应将收纳袋移入“不建议购买/可复用”。是否为 0 元方案取决于用户明确补充的物品，不能在默认案例中预先写死。

## 7. 产品状态与数据约束

- 场景模板是固定 JSON 数据；命中模板的第一轮清单可由确定性模板路径返回，不应描述成模型自由生成。未命中模板的场景理解和后续开放式解释可调用 LLM，实际是否调用以事件轨迹为准。
- 商品目录、价格和属性是本地模拟数据，不是真实可售供给。模型不得补造 SKU、价格、库存、配送或商品属性；由目录/规则校验可验证事实。
- 必备/按需是物品分类；已有/需要购买/不需要/未确认是用户状态，二者不可混为一组状态。`不需要` 与 `还不确定` 必须可区分；不需要项不会进入商品检索。
- 数量与条件是场景估算或模板参考，不是行业统一标准；医疗、宠物健康等专业内容不由 ShopMind 替代专业意见。
- 推荐方案最少需要：目标、边界条件、已有物品、必需品类、可选品类、不买项、用户优先级、预算、推荐商品、选择理由、取舍、不适用人群、未知信息、方案必买总额。
- 没有证据的字段为空/待确认，不能用默认“无”替代未知。
- 本 Demo 不接真实交易，不承诺库存、物流或商品目录之外的信息。

## 8. 验收标准

1. 新 session 命中已支持场景时，SSE 方案含正确 `template_id` 和非空 `checklist_sections`；清单呈现具体物品，而不是用概括槽位替代明细。
2. 未提及的物品保持未确认；已确认已有、不需要和未确认不会进入商品检索；只有明确需要购买的项目触发搜索。
3. 用户文字补充只改对应槽位；场景/预算/偏好变化按影响范围选择局部更新、过滤重排或全量重算，并保留未受影响的确认事实。
4. 商品候选需满足目标槽位与硬约束；模拟目录无匹配时明确显示缺口，不以相邻品类凑数。
5. 必备与按需的视觉分组可读，按需提供“这次要买 / 不需要 / 还不确定”；桌面、平板、手机分别为 3、2、1 栏。
6. 待产清单展示孕妇、宝宝、陪护人模块、具体项目和模板数量/条件；清楚标注 NHS 为英国参考、医院要求有差异，提醒以生产医院为准，不提供医疗建议。
7. 真实模型调用、模板路径、检索结果与分阶段耗时通过事件记录区分；不能把 HTTP 200 当成内容正确，也不能把字符串匹配代理值称为标准 Recall/Precision。
8. 所有演示或合成请求明确标识为测试数据，不暗示真实库存、真实用户行为或线上业务效果。

## 9. 竞争力验证指标

Demo 文案只能传达假设，不能证明壁垒。当前目录与价格均为虚拟数据；前端埋点只能提供交互过程、输出结构和用户主观体验，不能自动证明模型判断正确。后续可用固定场景、固定商品库和人工核对答案做模型评测。评估分三层：

### 前端可自动记录

- 任务与流程：场景编号、设备类型、完成时长、用户/助手轮数、澄清轮数、方案状态更新数、完成阶段、完成/部分完成/放弃。
- 决策结构：每轮任务槽位数、必需/可选/已有/不建议/待确认项数；最终推荐商品候选数。
- 预算与比较：预算上限、代码依据商品目录计算的必需最低总价、预算校验状态；加入比较及请求模型比较的次数。
- 技术与流失：错误次数、放弃阶段和原因。

### 测试者主观反馈

- 清单完整度、遗漏顾虑缓解度、预算理解度、取舍理解度、推荐可信度、决策信心、流程顺畅度（1–5 分）。
- 是否完成任务和完成到哪一步。

### 需要模型评测/人工标注，不能只靠前端行为推断

- 场景边界理解、关键追问命中率、必需槽位覆盖率、遗漏率、已有物品识别准确率、重复购买建议率、条件项误判率、商品与任务槽位匹配度、取舍解释忠实度、预算推荐是否合规。
- 对每个固定场景维护人工核对的参考槽位和目录事实，再计算正确率/召回率；点击、生成商品数量不能替代正确性。

同任务、同目录下与普通推荐流程对照时，至少观察：

- 用户是否能正确说出“必须买 / 可选 / 不买”的边界与总支出。
- 达成目标所需的追问轮数，以及用户是否能完成任务。
- 必要品类漏项率、重复购买建议率、预算超限率。
- 用户是否理解每个选择的代价、替代方案和未知信息，并对方案有决策信心。

不以推荐商品数、点击数或加购率作为首要成功指标；若产品主张是帮助用户少买却拿成交指标当唯一目标，产品激励会与定位冲突。

## 10. 当前 Demo 迭代范围

本地 MVP 当前包含 React/Vite 对话界面、FastAPI/SSE 会话接口、AgentScope MainAgent/SearchAgent、版本化方案与场景模板。Scene demo 使用实际 LiveChat/API；模板命中优先走确定性清单，开放式后续输入可使用模型。当前反馈 CSV 是本机研究工具，不是线上分析 SDK。登录、跨设备同步、真实 SKU/库存、真实下单与线上分析平台均不在当前 MVP 范围。

## 11. 历史性能回归（2026-10-22）与 2026-10-23 本地复核

| 错误 / 断联 | 0 | 本轮样本内未出现 |
| 首条有效反馈 | 平均 4.97s，P95 5.72s | 反馈回执，不是完整清单 |

| 商品候选 | 4 场景有候选、1 场景空召回；总计 12 张 | 不代表 12 张都与目标槽位匹配 |

### 与产品目标的差距及本轮调整

- **时延记录**：此 5 场景样本整轮 P95 约 15 秒，确认后的首批商品 P95 约 15 秒；项目尚未定义正式线上 SLO，仍需更多场景复测，不能视为稳定服务水平。
- **搜索有被调用，不代表搜索质量合格**：5/5 确认轮派发 SearchAgent，但家庭咖啡的“手冲咖啡滤杯”召回到了“手冲壶”等邻近品类；自驾场景没有可用商品。
- **产品决策**：以目录明确匹配优先于候选数量。清单槽位搜索增加任务名相关性过滤，未匹配商品不得展示或进入候选缓存；目录缺失时返回空候选/缺口提示，后续再补充可信目录，而非用相邻商品凑数。普通自由商品搜索不受该槽位过滤影响。
- **状态与流程保持不变**：MainAgent 仍维护状态和意图、SearchAgent 负责检索/过滤/排序，TradeAgent 继续休眠；用户逐项标记已有、待购或待确认后才搜索。

### 2026-10-23 本地复核补充

- **浏览器展示**：真实浏览器用全新 session 验收待产、租房和第一次养猫。待产实际渲染孕妇/宝宝/陪护人三模块（17/8/5 项），租房显示睡眠与照明/入住清洁/收纳与日常，养猫显示 5 个模块；桌面/平板/手机布局为 3/2/1 栏。该证据验证 UI 和模板数据到达页面，不验证清单内容本身的专业正确性。截图与 JSON：`eval/results/local_acceptance_20261023_feedback/`、`eval/results/local_acceptance_20261023_rental_demo/browser-final/`。
- **本地 API 回归**：当前隔离 API 对出行、开学、租房各跑“初始清单—确认—补充”三阶段，9/9 阶段通过；该轮 `model.call` 为 0，验证的是模板和目录链路，不是大模型质量。细节：`eval/results/aipm_data_evidence_20261023/core-flow-8013-current-anchor/mvp-core-three-20261023-195313.json`。
- **检索探索评测**：14 条海边/租房 Query、7 个槽位，K=8；已知槽位过滤配置的临时参考集 Recall@8 0.743、Precision@8 0.809、MRR 0.857。标注表 170 个候选的人工相关性、属性证据和理由仍为空，14 条 Query 均待标注；这些不能作为正式 Gold 指标或简历准确率。详情：`eval/results/aipm_data_evidence_20261023/recall-report-20261023-194110.md`。
- **模型证据**：一次租房开放式追问观察到 DeepSeek-V3.2 模型调用，模型事件耗时 11.062 秒，没有质量评分；不足以估算模型时延分布，也不能证明模板首轮由模型生成。

以上证据只支持“当前本地版本的固定模板与交互链路能运行”。用户需求价值、清单内容正确性、开放表达下的模型增量、商品推荐质量、真实 SKU 可买性和业务转化仍未验证。

### 下一轮评测门槛

下一轮必须同时看业务指标和模型/系统指标，并分开报告：

1. **业务正确性**：参考清单必需槽位召回率、必需/按需分类准确率、已有物品识别率、重复购买建议率、任务槽位商品匹配率、目录覆盖率、预算合规率；关键项由固定参考答案或人工复核，不用候选数量替代正确率。
2. **模型质量**：结构化状态有效率、意图/变更分类准确率、错误状态迁移率、解释与目录事实一致性；SearchAgent 每次执行的决策及候选须可追溯。
3. **时延与可靠性**：首条反馈、首份清单、首批商品、整轮结束分别报告平均值与 P95；同时记录请求成功率、断联/超时、每轮模型调用数和输入/输出 Token。
4. **成本与用户结果边界**：账单成本需从供应商账单或可验证 usage 采集；模拟场景不声称满意度、真实任务完成率、转化或 ROI。未来进入真人测试后再收集决策信心、清单完整感与完成率。

2026-10-23 的搜索修正验收只覆盖“候选不得错槽位”这一规则和已有本地回归；目录覆盖、自驾商品召回与真实用户价值仍未证明。

## 12. MVP 范围、优先级与阶段验收

### MVP 判断

MVP 不要求先实现登录、跨设备同步或长期用户画像。功能范围是让用户在一个购物任务内完成“看到具体且分类清楚的清单 → 逐项标记已有/需要购买/不需要/未确认 → 只为明确待购项搜索 → 得到同品类候选或明确的目录缺位说明”。当前本地版本已有模板、状态交互、增量检索与浏览器展示证据；但清单内容质量、检索相关性金标和真实用户价值尚未通过验证。因此当前状态是**功能原型可本地验收，产品效果未验证**，不能写成已完成市场验证的 MVP。

### 优先级

| 优先级 / 状态 | 能力 | 当前证据 / 下一步要求 | 暂不包含 |
| --- | --- | --- | --- |
| 已实现 / P0 验证 | 场景模板与模块清单 | 当前 JSON 模板覆盖出行、开学、租房、待产、第一次养猫；SSE 和浏览器测试验证模板 ID、分组数据、明细和响应式布局。后续要双人复核完整性、必要性、数量和条件。 | 模板编辑器、个性化模板学习 |
| 已实现 / P0 验证 | 用户确认与状态变更 | 必备和按需是物品类型；已有、购买、不需要、未确认是用户选择。按需 UI 已支持“这次要买 / 不需要 / 还不确定”；未知和不需要分开存储，只为明确待购项搜索。继续补充冲突/否定/改口等开放表达评测。 | 自动推断用户所有权或替用户决定购买 |

### 端到端验收用例与当前状态

固定用例用于回归，不代表完整的线上用户任务覆盖：

1. 用户只描述周末海边两天，模板快速生成可核对清单，明确区分核心核对项与按需项；泳衣、泳镜分别列项，饮料按条件标记为按需，个人药品只作为自备提醒，不自动给药品建议。
2. 未提及的物品显示待确认；用户可独立标记“泳镜已有、泳衣需要购买、防晒霜待确认”等事实，MainAgent 不把一个物品状态套用到同类其他物品。
3. 确认后只把“泳衣”这一明确待购槽位交给 SearchAgent。目录有匹配时返回同类模拟泳衣候选；没有时返回清晰的目录缺位说明。禁止展示颈枕、玻璃杯等无关商品。
4. 用户修改待购状态后，SearchAgent 根据完整方案与 mutation 进行局部召回、过滤/重排或必要的重新召回；TradeAgent 继续休眠。
5. 保存逐轮对话、状态快照、事件、候选及各阶段耗时；逐项复核业务参考答案和商品槽位匹配，不只核 HTTP 成功。

本地已覆盖出行、开学、租房三场景 API 三阶段回归，以及待产、租房、第一次养猫浏览器展示。下一阶段不再以“模板是否能显示”为主要目标，重点转向清单内容评审、检索标注和模型/规则基线对照。

### MVP 量化门槛与报告口径

- **清单业务质量**：必需核对项召回率、按需/条件项分类准确率、关键遗漏数、已有物品状态识别准确率、用户修改后的状态变更正确率。每个固定场景需先有人工核对的参考答案；模板建议与用户事实分开计分。
- **搜索业务质量**：商品-任务槽位匹配率（MVP 要求 100% 不出现跨类候选）、目录覆盖率、明确缺位说明率、预算硬约束合规率。目录缺位时的正确空结果优于无关候选。
- **模型/系统质量**：结构化方案有效率、搜索调度正确率、HTTP 成功/错误/断联/超时、分阶段耗时平均值与 P95、模型调用次数与输入/输出 Token。
- **本地功能验收状态**：当前浏览器和 API 核心链路有本地产物，见上方证据路径；不等于内容质量或真实用户价值验收通过。
- **产品质量通过条件**：冻结清单与商品参考答案；双人标注并处理分歧；固定场景与未见表达分别评测；开放场景对照模板/规则与 LLM；报告分阶段时延和失败案例。阈值须在标注前定义，不能根据结果倒推通过线。
- **明确不作为 MVP 通过证据**：请求成功、商品卡数量、模板命中本身不等于清单正确；合成场景不证明真实用户满意度、真实任务完成率、转化或 ROI。
