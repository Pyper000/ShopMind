# ShopMind 产品需求文档（PRD）

版本：0.4 文档基线 · 2026-10-25 · 本地 MVP。文档版本不代表软件已发布。配套：[作品集](portfolio/README.md)、[交互原型说明](portfolio/02_需求与原型/交互与原型说明.md)、[评测证据](portfolio/04_评测与数据/评测与证据.md)。

## 1. 背景、用户与问题

目标用户假设：正在处理首次或陌生的多品类生活任务，需要核对具体物品、适用条件和本次可用资源的人。创始人欧洲旅行经历及匿名个案提供方向；短途出行靠记忆、到场补购、养猫先基础后升级是必须保留的反例。样本未去重，尚未证明普遍需求。

JTBD：当我面对不熟悉的生活任务，希望把零散建议变成适合本次情况的准备清单，确认我能复用和需要补齐的物品，从而更有把握完成准备，并减少无用采购。

痛点与需求映射：

| 痛点 | 需求 | 用户价值及验证方式 |
| --- | --- | --- |
| 多来源建议难整理，适用性未知 | 模块化具体项目、条件与来源 | 看用户整理耗时、增删项目及关键遗漏 |
| 记得拥有，但本次未必能用 | 显式已有/准备/未知/不需要；允许更正 | 看重复采购、错误状态和修订成本 |
| 通用“衣物”无法执行 | 城市、日期、天数、同行对象、活动对应类别和数量 | 看用户是否仍需追问套数、错配气候或漏儿童用品 |
| 清单直接导购带来过度购买与信任问题 | 非商品隔离，仅检索明确待购缺项 | 看无关候选、误触发搜索和主动不买行为 |
| 一次回答后无法迭代 | 会话恢复、反馈、自报结果与候选治理 | 看真实复用/反馈；机制通过不等于效果成立 |

## 2. 目标与范围

业务目标：验证清单是否帮助用户完成准备决策。成功可以是全部复用、不买任何商品。当前不以 GMV、商品曝光或自动下单为核心目标。

模型目标：正确识别目标与对象、保持多轮约束、输出可执行分组清单、必要追问、遵守用户事实与目录事实。模型无需每轮都调用；可由模板/规则稳定完成的任务走快速路径。

| 优先级 | 范围 | 当前状态 |
| --- | --- | --- |
| P0 | 对象兼容路由、统一清单结构、显式状态、非商品隔离、待购检索 | 有实现与本地验收 |
| P0 | 已知模板、语义改写、冲突对象、新场景回归 | 有固定样本与自动化断言 |
| P1 | 一键清单反馈、自报购买结果 | 已实现并有接口验收，真实效果待采集 |
| P1 | 游客保存、可选本地账号、授权库存/偏好 | 已实现并有测试；非生产级身份系统 |
| P1 | 去标识化候选、结构评测、人工发布/回退 | 已实现并有本地流程验收 |
| P1 | 气候、天数、成人/儿童、活动约束完整旅行清单 | 天气基础已验收；最新多轮细分仍待验收 |
| 不在本版 | 真实 SKU、支付/物流/订单、自动交易、自动发布模板、已证明的转化提升 | 未接入/未验证 |

## 3. 核心流程与状态

任务输入 → 识别场景和条件 → 模块清单 → 用户核对 → 确认缺项与预算 → 商品候选 → 确认演示方案 → 反馈或之后回来更新。

必备/按需是建议属性；用户状态如下：

| 页面状态 | 数据含义 | 后续行为 |
| --- | --- | --- |
| 还没确认 | unknowns | 保留未知，不搜索 |
| 已有 | reusable | 会话内复用，不推断同类物品也已有 |
| 需要准备：可购商品 | 经确认进入 must_buy 或 optional_buy 对应流程 | 同槽位候选检索；无供给则提示缺口 |
| 需要准备：非商品 | prepared | 携带/办理核对，不进入商品搜索 |
| 不需要 | not_buy / deferred 对应提交 | 本次排除，不等于永久不喜欢 |

兼容旧接口的 must_buy/optional_buy 保留；页面统一“需要准备”。prepared 表示用户声明需要携带/办理，不表示证件已办理完成。购买结果、建议属性和本次准备状态均不可互相推导。

## 4. 数据契约与业务约束

ShoppingPlan 至少包含 goal、stage、state_version、template_id/version、checklist_sections、tasks、optional、must_buy、reusable、prepared、not_buy、unknowns、budget_major、preferences、prep，以及可选 weather_context。

清单契约：

- 新场景输出 2–6 个有意义模块，各模块都有 required 和 optional 数组，允许某数组为空。
- 每项是可单独确认的具体物品；支持 name、quantity、condition、note、purchasable。不把“旅游用品”“必备物品”当成唯一槽位。
- 顶层 tasks 等于模块项目去重集合；顶层 optional 等于模块按需集合。统一由工具/应用层校验。
- 单份领域方案上限为 32 项；部分选择 DTO 数组上限为 24，当前存在容量口径差异，需验证大清单提交边界。
- 不知道用户是否拥有时保持未知；只有用户明确事实或授权可用记忆能更新状态。
- 商品、价格、规格和配送事实来自目录；无证据的字段待确认，不能由模型补造。
- 每槽位候选互斥选择；总价按所选目录价格计算。清单数量目前为文本估算，尚未统一为可计算采购数量，不能宣称已按衣物件数完成整单报价。

## 5. 旅行清单专项需求

| 输入/条件 | 目标输出与处理 | 验证状态 |
| --- | --- | --- |
| 城市+确切日期 | 获取该城市气温、降雨/降雪等，标来源及时间；按日期区间计算天数 | 有预报 SSE 记录 |
| 城市+3天，无日期 | 给天数估算，追问日期；不猜短袖、雨雪 | 已有基础验收 |
| 日期超预报窗口 | 可用历史同期数据时标“气候参考，非预报”；不可用则降级 | 有历史参考验收，覆盖有限 |
| 同行本人和5岁孩子 | 分开本人/儿童衣物与数量；不能丢已有日期、地点、天数 | 最新需求，完整多轮验收未完成 |
| 计划下水游泳 | 泳衣/泳镜带下水条件；未计划下水不默认必备 | 尚需统一模板与追问行为 |
| 雨天 / 雪天 | 雨具与防滑防水/保暖品项带条件，不能把雪当雨 | 雨雪规则有单测，需多轮组合验收 |
| 更换旅行模板 | 区分补充活动与新行程；保留适用事实，变化地点日期需重取天气 | 待专项验证 |
| 服务失败/地点歧义 | 显示未知/候选城市；保留基础清单，天气失败不阻断整个任务 | 有降级单测 |

数量基线是可调整估算：上衣按每天1件+1件备用，下装轮换，内衣袜子按天数+备用；儿童备用、洗衣条件、拍照穿搭、长途/多城市安排应由明确约束调整。完整“本人/儿童+天气+活动+天数”规则还未验收为完成，原型展示目标交互。

## 6. 反馈、会话与授权

- 清单反馈：helpful / needs_work；购买自报：bought / not_found / chose_not_to_buy / not_yet。
- 同一 session_id + kind 更新同一记录，不因多次点击累加分母；当前聚合按会话而非自然人/方案版本。
- 刷新恢复同机对话；“新对话”创建新 session。浏览器保存不等于跨设备同步。
- 游客身份由后端隔离；本地登录可选。登录不自动开启长期记忆，默认 consent=false。
- 授权后才可跨会话读写库存/偏好；撤回后停止读取；清除记忆可删除相关记录并撤回授权。库存“拥有”仍不保证本次可取用。
- 目前没有自然人去重、反作弊及完整生产分析平台；不得将测试反馈当真实效果。

## 7. 模板治理

用户主动同意 → 提交匿名结构化模块 → 基础敏感信息检查 → pending → 结构评测 → 人工批准/拒绝 → 版本发布 → 必要时回退。

禁止原始 query、session_id 或账号随候选提交；基础格式过滤不能保证完全匿名，审核仍须看内容。结构评测只检查契约，不等于专业内容正确。审核接口目前限定本机来源，公网反向代理可能改变来源判断，正式发布前需独立审核员认证。

商品 CandidatePool 是检索缓存；模板候选池是内容治理数据，两者独立。候选变模板不涉及微调模型。

## 8. 异常、风险与验收标准

| 用例 | 通过标准 | 验收方式 |
| --- | --- | --- |
| 成年猫语义改写 | first_cat_home，多模块具体物品 | 路由单测 + SSE |
| 成年狗 | 不命中猫；开放场景2–6模块 | 冲突单测 + SSE |
| 新社区活动 | template_id为空、结构一致、非泛槽位 | 开放模型 SSE + 人工看内容 |
| 确认猫粮、已有食盆 | 只检索猫粮，已有不搜索 | plan.update / agent / tool 事件 |
| 护照需要准备 | prepared，不进入待购 | 工具/接口测试 |
| API未知路径 | JSON 404；不能HTTP 200 HTML | HTTP与Content-Type |
| 未授权写记忆 | 拒绝；撤回后不注入记忆 | API/会话测试 |
| 未评测候选直接发布 | 拒绝，评测后人工发布可回退 | 治理测试 |
| 旅行多轮组合 | 天数、气候、对象、活动无丢失；集合一致 | 待补专项用例 |
| 高UV天气 | 不报错并有来源化防晒提示 | 当前确认存在未覆盖缺陷，未通过 |

完整测试与已知失败见[评测文档](portfolio/04_评测与数据/评测与证据.md)。上线需以当前源码重新验收；历史阶段完成不意味着后续扩展自动达标。

## 9. 指标、实验与发布判断

当前工程结果：395 passed、1 warning，前端构建通过；阶段1–5已有特定时点本地闭环记录。没有正式线上 A/B，也没有用户价值胜出结论。

拟验证业务指标：真实任务独立完成率、完成耗时、关键遗漏/冗余、决策信心、主动采用/放弃原因。模型指标：对象误路由、结构合法、原子项可执行、事实保持、误触发检索、目录相关性、分阶段时延和成本。

指标分母、阈值设定依据和 A/B 设计见[评测与证据](portfolio/04_评测与数据/评测与证据.md)。先做同任务可用性对照与人工内容审查，再根据基线设计线上实验。
