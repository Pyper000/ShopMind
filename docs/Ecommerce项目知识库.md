> 使用方式：用于产品方案、简历、面试和后续迭代，不作为真实线上业务或个人全栈开发证明。

## 1. 一句话定位

Ecommerce 不是“给电商套一个聊天框”，而是把跨境购物中的模糊表达，编排成一条可解释的搜索与决策链路：

`用户需求 -> 意图与约束理解 -> 商品检索/筛选 -> 推荐或无结果解释 -> 确认式行动`

它要解决的核心问题是：用户往往把品类、属性、预算、目的国、到手价和下单意图混在同一句话里；传统关键词搜索只能返回结果，无法解释结果为什么合适、为什么没有结果、下一步应该如何行动。

## 2. 目标用户与业务问题

### 目标用户

- 有明确任务但表达口语化的跨境购物用户，例如“人在香港，想买一个床，应该怎么买”。
- 有硬约束的用户，例如预算、目的国、材质禁忌、库存、到手价。
- 处于决策阶段的用户，例如比较两个商品、询问税费、确认是否下单。

### 五类业务痛点

1. **Query 表达与商品结构不一致**  
   用户说“便宜、抗造、不要塑料”，商品系统却按品类、材质、价格、库存等结构化字段组织。

2. **跨境硬约束容易导致假性无结果**  
   用户看不到“有商品，但超预算”或“商品可买，但目的国不可达”，容易把约束过滤误解为平台无供给。

3. **结果列表不能完成购买决策**  
   仅有商品标题和价格不足以支持跨境购买；用户还需要到手价、选购理由、差异说明和比较结论。

4. **搜索到交易之间存在误操作风险**  
   下单、取消等写操作不能由模型根据模糊表达直接执行，需要明确确认、身份隔离和事实校验。

5. **搜索质量难以只靠“回复好不好”评估**  
   需要区分相关性、硬约束正确性、无结果解释、交易安全和多轮记忆等不同问题。

## 3. 产品范围与边界

### 当前能力

- 商品找寻、推荐、对比和跨境到手价说明。
- 选购知识问答，例如材质、价格带、避坑点。
- 长期偏好记忆，例如“不要塑料材质”。
- 模拟订单的确认、创建、查询和取消。
- 事件时间线展示“理解了什么、查了什么、为什么这样推荐/拒绝”。

### 明确不做

- 不接真实用户、账户、支付、物流、订单或企业搜索日志。
- 不承诺真实退款、发货时效、税务政策或线上业务增长。
- 不把课程中的工程代码、指标或结论自动写成个人独立贡献。

## 4. 搜索决策 SOP

### 步骤 1：识别用户要完成的任务

将表达归为以下任务之一：

- 找商品 / 推荐商品
- 询问选购知识
- 比较商品
- 查询到手价
- 创建、查询或取消模拟订单
- 写入或撤回长期偏好

### 步骤 2：抽取 Query 槽位

优先识别：

- 品类：露营灯、耳机、旅行三件套等。
- 属性：抗摔、轻便、无塑料、军绿色等。
- 预算：金额与币种。
- 目的国：影响可达性、运费和关税。
- 用户偏好：长期材质禁忌或风格偏好。
- 行动状态：仅咨询、比较、准备下单、已经确认。

### 步骤 3：决定搜索策略

- 有明确品类和约束：直接检索并结构化过滤。
- 用户先问“怎么挑”：先给品类判断口径，再检索具体商品。
- 多个独立品类或深层筛选：拆为并行或隔离子任务。
- 仅简单查询：不为了“多 Agent”而额外转交。

### 步骤 4：组织候选与解释

候选输出至少回答四件事：

1. 推荐什么。
2. 为什么符合用户需求。
3. 到手价由什么组成。
4. 哪些商品被过滤，以及被什么约束挡住。

### 步骤 5：处理无结果

无结果不能只回复“没有”。需要先归因：

| 无结果类型 | 业务解释 | 下一步 |
| --- | --- | --- |
| 真无供给 | 商品目录没有该品类 | 明确说明供给缺失，给相近品类或订阅建议 |
| 被预算过滤 | 有商品但超预算 | 告知超出金额，建议放宽预算或替代商品 |
| 目的国不可达 | 有商品但当前不可寄达 | 说明可达性限制，建议切换目的国或同类可寄商品 |
| Query 不完整 | 未说明预算、目的国或关键属性 | 只追问一个影响最大的缺失信息 |
| 工具不可用 | 无法取得商品/价格事实 | 如实说明数据不可用，不编造价格或库存 |

### 步骤 6：确认式行动与反馈

- 下单或取消前展示确认卡：商品、数量、金额、地址。
- 只有用户明确确认后，才执行模拟写操作。
- 将长期偏好与一次性要求区分：前者可跨会话记忆，后者仅影响本轮。
- 通过结果反馈、无结果原因和用户修改条件，为后续 Query 策略迭代沉淀样本。

## 5. 三个 Agent 的产品分工

### MainAgent：搜索决策编排

**解决的痛点：** 用户的自然语言诉求往往跨越搜索、选购咨询、比较和交易；若每个问题都强制转给子 Agent，反而增加时延与上下文丢失。

**产品职责：**

- 维护多轮意图、长期偏好和当前确认状态。
- 决定直接处理还是派发 SearchAgent / TradeAgent。
- 仅在“可并行、上下文需要隔离、内部调用链较深”时进行任务拆分。
- 将内部工具调用合成为用户能理解的推荐、解释和下一步。

**面试表达：** MainAgent 的价值不在于“调度了几个 Agent”，而在于把搜索任务转成正确的决策路径，并避免无意义的多 Agent 转交。

### SearchAgent：相关性与无结果治理

**解决的痛点：** 模糊 Query、硬约束、品类知识和供给状态混在一起时，容易出现不相关推荐、超预算推荐或假性无结果。

**产品职责：**

- 将口语 Query 规范化并抽取品类、属性、预算、目的国等槽位。
- 结合选购知识形成检索与排序口径。
- 组织向量召回、精排和关键词降级，以保障不同可用条件下仍能返回结果。
- 将价格和可达国作为结构化过滤条件，并回传过滤原因。
- 返回符合偏好的商品与可解释的替代/放宽建议。

**面试表达：** SearchAgent 的关键不是“用了向量库”，而是把“找不到”拆成供给、约束、表达和系统四类问题，避免给用户错误结论。

### TradeAgent：从决策到行动的确认闭环

**解决的痛点：** 购物搜索最终会进入行动阶段，模型不能凭模糊语句自行创建或取消订单。

**产品职责：**

- 处理模拟订单创建、查询和取消。
- 接收由主 Agent 管理的用户确认信号。
- 隔离买家身份上下文，所有金额和状态均来自工具返回。
- 对订单不存在、库存不足等异常给出事实性反馈。

**面试表达：** TradeAgent 不追求炫技，而是让“推荐”能够安全地走向“行动”，用确认机制建立用户信任。

## 6. 搜索策略与产品规则

### 硬约束与软偏好

- **硬约束：** 预算、目的国可达性、库存、长期材质禁忌；不满足时不能直接推荐。
- **软偏好：** 风格、颜色、轻便程度；用于排序和推荐理由。
- **业务原则：** 预算和目的国等临时条件不应自动跨品类沿用，除非用户明确表示“还是这个条件”。

### 结果可解释性

用户应能理解：

- 为什么推荐它：属性、价格、偏好、目的国匹配。
- 为什么没有推荐某商品：超预算、不可寄达、库存不足或偏好冲突。
- 为什么需要追问：缺少会改变结果的关键槽位。
- 为什么不能执行：尚未确认、订单不存在或能力边界不支持。

### 搜索质量的业务口径

| 维度 | 业务问题 | 可观察信号 |
| --- | --- | --- |
| 有效结果率 | 用户能否拿到可购买候选 | 有候选且满足硬约束 |
| 相关性 | 推荐是否理解了用户意图 | Query-商品匹配、属性命中、排序合理 |
| 无结果解决率 | 无结果后用户是否知道下一步 | 归因准确、给出替代或放宽建议 |
| 决策效率 | 用户是否更快完成比较和选择 | 查询轮数、比较后确认率 |
| 行动安全 | 是否避免误下单和事实编造 | 未确认写操作率、金额/状态事实错误率 |

以上为后续真实业务或模拟日志可使用的指标框架，当前不是线上指标。

## 7. 现有评测资产与结论

### 已沉淀的评测场景

13 条端到端回归场景覆盖：

- 预算硬约束检索。
- 跨境到手价与税费说明。
- 两商品到手价比较。
- 下单前确认卡、下单-查单-取消闭环。
- 长期偏好写入与跨会话生效。
- 真无供给、订单不存在、闲聊边界。
- 品类知识问答、多轮上下文和工具不可用时如实告知。

### 已沉淀的检索评测

- 商品召回标注：67 条 Query，其中 55 条字面类、12 条语义类。
- 品类知识标注：22 条。
- 模拟商品目录：69 个 SPU。

### 记录中的验证结果

以下结果仅适用于项目文档记录的模型、模拟商品与评测集，不等同于真实业务表现：

- Qwen-plus 配置下，13 条端到端回归场景为 13/13 通过，均分 0.988。
- 当前复跑商品检索 Recall@8 为 0.871；硬约束过滤准确率为 1.000。历史文档中的 Recall@8=0.978 与当前复跑不一致，以当前可复现结果为准。
- 关键词降级在语义 Query 上的召回明显低于向量检索，说明降级可用不等于体验等价。

3. **比较到确认：** 展示商品对比、确认卡和模拟下单，说明搜索如何服务购买决策。

## 9. 60 秒项目讲述

我把 Ecommerce 定义成一个跨境购物搜索与决策 Agent。它解决的不是“能不能搜到商品”，而是用户把预算、属性、目的国和购买动作混在一句话时，系统如何给出相关、可买、可解释的结果。

产品上我把链路拆成三个角色：MainAgent 负责识别用户处于搜索、比较还是确认阶段，并决定是否需要拆任务；SearchAgent 把口语 Query 转成品类和约束，重点解决相关性和假性无结果；TradeAgent 把推荐后的行动收进确认机制，避免模型直接执行交易。

验证上，我用预算、跨境到手价、无结果、长期偏好和确认下单等 13 个场景做回归，并用 67 条 Query 看召回和硬约束正确性。这个项目让我更关注搜索产品的核心判断：结果是否相关、无结果是否说清、以及用户能否安全地从搜索走到决策。
